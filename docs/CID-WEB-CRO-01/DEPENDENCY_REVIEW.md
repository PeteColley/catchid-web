## Actual delivery and input boundaries

**Visitors:** `astro.config.mjs` sets `output: "static"`, with no adapter. The inspected `dist/` has 42 files: two HTML pages, CSS, images, sitemap, robots and CNAME. No Node server, dependency bundle, source maps, client islands or standalone JS artifacts are delivered. Each page contains exactly the unchanged inline consent/attribution script; Google analytics is loaded only after consent. Visitor query parameters are handled by browser URL APIs in that script, not sent to a Node renderer or any audited library. No JSX/MDX renderer, View Transition API, content collections, Astro actions or sessions are configured. A static page could still contain build-time injected code; the actual source inputs and generated scripts were checked, rather than treating static output as sufficient proof.

**Production runtime:** `.github/workflows/deploy.yml` uploads the static output using `withastro/action@v6` and publishes it with `actions/deploy-pages@v5`. [GitHub Pages is static hosting](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages). There is no candidate Astro/Vite/Node production runtime or public image-transform endpoint. This reviews the repository's publication path; it does not claim a new deployment or inspect GitHub's internal hosting implementation.

**Local development versus preview:** scripts explicitly bind both to `127.0.0.1`. However, `devToolbar: false` does **not** disable Vite's `/__open-in-editor` middleware: it is registered unconditionally in installed `vite/dist/node/chunks/node.js`. Do not regard loopback as immunity to malicious-browser-to-localhost requests. Installed Astro static preview uses Vite `preview`, `appType: "mpa"`, and a static-file stack without the development editor or Wasm-transform handlers. No development/preview server or exploit was started for this review.

**Build/CI:** workflow runs on main push or manual dispatch, not `pull_request`/`pull_request_target`; no issue/comment/payload interpolation or external CMS/user uploads feed the build. It checks, builds and verifies checked-out source. The Ubuntu runner is relevant to Sharp's Linux advisory. Build has `contents: read` and checkout disables persisted credentials; deployment permissions are in a separate job. These limit consequences but do not make code execution safe. Repository source, package tarballs/install scripts, Actions and caches remain trust boundaries.

The current [withastro/action v6 implementation](https://raw.githubusercontent.com/withastro/action/v6/action.yml) performs an initial package-manager **install before** this repository's custom lockfile-diff guard and `npm ci`. It then uploads `dist` by default. Thus the guard prevents publishing a changed lockfile but does not sandbox the earlier installation. Mutable action tags, Node 24 selection, registry and cache provenance are existing supply-chain dependencies, not covered by npm's candidate-lockfile audit. No specific advisory exploit path through that initial install was identified. Pinning actions and using one explicit `npm ci` install are follow-up hardening recommendations, not changes made here.

## Follow-up, uncertainty and self-review

1. Separately authorise targeted dependency maintenance using the minimum versions above; prioritise **Vite 8.2.4** before resuming dev-server work, then **Sharp 0.35.5**. Meanwhile use the existing static build/loopback preview for review, keep dev servers closed when not needed, and do not expose them or ingest untrusted assets. No server was started/stopped by this task.
2. Re-audit, check, build and verify after any remediation. Do not assume upgrading Astro alone refreshes all vulnerable transitive lock entries. All fixes are recommendations only.
3. Node's bundled undici is separately **7.29.1** locally, not the audited npm copy 8.10.2. Several upstream advisories also cover it. A future tooling update should select a supported Node release containing patched undici (at least 7.30.1 on that line); updating the npm package alone does not patch Node's embedded copy. No SSE/WebSocket/custom TLS/cache trigger or attacker-selected outbound peer was found in this candidate. Future CI Node resolution has not been executed or attested by this review.
4. No exploit or production probing was performed. Assessment is source/configuration/output inspection, official advisory review and deterministic verification, not a penetration test or universal guarantee. No new CI run was dispatched; Linux binary hardening, branch-protection settings, external action/cache integrity and future peer compromise are not independently attested. These residual uncertainties do not identify a trigger for the listed advisories in this exact publication path.
